# Seeding starting ratings (`seed-ratings-export`)

Gives every problem a difficulty-aware **starting** rating in ProblemCloud's
`public.problem_ratings` instead of the flat default `1500`. The scraper knows each
test's structure, so it does all the computation and emits a single, idempotent SQL
file that ProblemCloud just runs after a content sync.

```bash
bun cli/index.js seed-ratings-export [outfile] [--overwrite-seeds]
# default outfile: scrape_data/seed_ratings.sql
```

Run it **after** a sync (see `cli/SYNC.md`) — the file joins to `public.problems` on
`sync_key`, so the problems must already exist in the cloud.

## What it does

For each test, the policy in [`rating_policy.js`](../rating_policy.js) picks a
`[lower, upper]` rating band, then spreads that band across the test **by problem
number `n`** along a curve. Harder problems (higher `n`) get higher priors.

```
t    = (n - min_n) / (max_n - min_n)     // over THIS test's own problems
linear:  seed = lower + (upper - lower) * t
exp:     seed = lower * (upper / lower) ** t   // geometric interpolation
seed = round(seed)
```

A one-problem test (`max_n == min_n`) uses `lower`. The spreading unit is a single
test instance (e.g. the *2019 State Sprint*), normalized to its own `n` range.

## The policy (`rating_policy.js`)

```js
export const RATING_POLICY = {
  version: 1,
  fallback: { range: [900, 2100], curve: "linear" }, // or null to skip unmatched tests
  rules: [ /* … */ ],
};
```

A **rule matches a test when every field it specifies matches**:

| field               | matches against        | note                                                        |
| ------------------- | ---------------------- | ----------------------------------------------------------- |
| `series`            | exact `series.name`    |                                                             |
| `test_type`         | exact `tests.type`     | (mostly empty in the DB today; most rules skip it)          |
| `test_name_pattern` | `tests.name` substring | case-insensitive; **an array means every token must appear (AND)** |
| `range`             | —                      | `[lower, upper]` band                                       |
| `curve`             | —                      | `"linear"` (default) or `"exp"`                             |
| `priority`          | —                      | higher wins on multi-match (default `0`); ties break by array order |

The array form of `test_name_pattern` is how competition **levels** are told apart:
`["State", "Sprint"]` vs `["National", "Sprint"]` vs `["School", "Target"]`, each with
its own band. Give the specific level+round rules a higher `priority` than the bare
single-token fallbacks (`mc-sprint`, `mc-target`, `mc-team`) so a named level wins and
only unrecognized ones fall through.

Ranges are **priors** — tune them freely. Unmatched tests get `fallback` (or are
skipped if `fallback` is `null`).

## Modes — the `--overwrite-seeds` flag

The two modes differ **only** in the `on conflict` `where` clause. A freshly-synced
problem may have no `problem_ratings` row yet, so the file always **upserts** (a new
problem is always inserted).

- **Default — seed-then-lock (no flag):** only rows still at the untouched default
  (`attempts = 0 AND rating = 1500`) are seeded. Safe and re-runnable — never clobbers
  a rating that play or a previous seed has already moved.
- **`--overwrite-seeds` — full re-tune:** the `where` clause is dropped, so **every**
  matched problem is re-seeded to the config value regardless of current state. Use it
  deliberately to push a re-tuned policy over already-seeded or already-played problems.

**RD reset:** in either mode, any write that actually **changes** a problem's `rating`
resets `rd` to `350` (full uncertainty). A seed that leaves the rating unchanged leaves
`rd` alone. This matters in overwrite mode, where re-seeding a played problem must also
throw away its accumulated confidence.

## Output

One idempotent statement (a single `VALUES` list), plus a header comment recording the
mode, per-rule match counts, and the `psql` run instruction:

```sql
-- Generated by aops-scrape `seed-ratings-export`. Seeds public.problem_ratings.rating.
-- Mode: seed-then-lock (default)
-- Rule match counts:
--   purple-comet: 1016
--   amc-8: 992
--   …
begin;

insert into public.problem_ratings (problem_id, scope, rating, rd)
select p.id, 'overall', v.seed::real, 350
from (values
  ('aops…n…1', 800),
  …                              -- one row per matched problem
) as v(sync_key, seed)
join public.problems p on p.sync_key = v.sync_key
on conflict (problem_id, scope) do update
  set rating = excluded.rating,
      rd     = case when public.problem_ratings.rating is distinct from excluded.rating
                    then 350::real
                    else public.problem_ratings.rd end,
      updated_at = now()
  where public.problem_ratings.attempts = 0        -- default mode only …
    and public.problem_ratings.rating   = 1500::real;  -- … dropped with --overwrite-seeds

commit;
```

`sync_key` uses the same `chr(31)` (`\x1f`) delimiter as the content-sync staging load
(`testSyncKey`/`problemSyncKey` in `src/export.js`) — the file carries the real `0x1F`
bytes, and `scope` is `'overall'` (the only scope today).

If no test matches a rule (and there's no `fallback`), the file contains only the
header comment — no `insert`.

## Applying it

```bash
bun cli/index.js seed-ratings-export scrape_data/seed_ratings.sql
psql "$CLOUD_DB_URL" -f scrape_data/seed_ratings.sql
```

**Note:** a later `public.recompute_ratings()` (full rating rebuild) resets every
problem back to `1500` before replaying the match log, so this is a **starting prior
applied to the current table** — re-run the file after a recompute if cold problems
need the spread again.
